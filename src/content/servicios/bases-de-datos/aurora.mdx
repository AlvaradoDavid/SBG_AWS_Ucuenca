## Descripción

Aurora es lo que ocurre cuando se rediseña una base de datos relacional asumiendo desde el principio
que corre en la nube. Mantiene la compatibilidad con PostgreSQL y MySQL — la aplicación no cambia —
pero sustituye la capa de almacenamiento por un sistema distribuido propio.

Ese cambio es el que explica todo lo demás. El almacenamiento guarda seis copias repartidas en tres
zonas de disponibilidad y es común a todas las instancias del clúster, así que añadir una réplica de
lectura no implica copiar datos y la conmutación ante un fallo se mide en decenas de segundos.

## Cómo funciona

1. Creas un **clúster** con una instancia de escritura y, si quieres, varias de lectura.
2. Todas comparten el mismo **volumen distribuido**, que crece solo conforme entran datos.
3. La aplicación escribe en el punto de conexión de escritura y lee en el de lectura, que reparte
   las consultas entre las réplicas disponibles.
4. Ante un fallo de la instancia de escritura, una réplica asume ese papel automáticamente.
5. En la modalidad **sin servidores**, la capacidad sube y baja sola con la carga, sin instancias fijas.

## Manos a la obra

- Crea un clúster de Aurora PostgreSQL con la instancia más pequeña disponible y **una alarma de
  presupuesto antes de empezar**: aquí no hay capa gratuita.
- Carga una tabla con datos de ejemplo y añade una réplica de lectura.
- Compara el tiempo de creación de esa réplica con el de una réplica en RDS estándar.
- Usa la clonación rápida para crear un entorno de prueba y comprueba que tarda minutos.
- **Borra el clúster completo al terminar**, incluidas las instantáneas finales.

La regla práctica para elegir entre Aurora y RDS es honesta: en un proyecto de club o de clase,
RDS con la capa gratuita casi siempre gana; Aurora empieza a tener sentido cuando hay tráfico real
y la indisponibilidad cuesta dinero.
